** Décisions confirmées

*** architecture

odoo est le système d'enregistrement unique. django ne possède aucun modèle métier : il sert de façade web/api, porte les sessions techniques et appelle odoo par une passerelle centralisée. un stockage technique futur de sessions, files ou caches ne devra contenir aucun objet métier odoo.

le module odoo =csrs_reporting= réutilise =res.users=, =res.partner=, =hr.department=, =hr.employee=, =project.project= et =project.task=. le premier lot étend =project.task= avec un responsable csrs, une révision optimiste et une progression; chaque évolution crée une entrée append-only =csrs.progress.entry= dans la même base odoo.

le portage n'est pas une réplication automatique des tables de =csrs_report=. chaque capacité est rapprochée d'un modèle odoo standard, puis complétée dans odoo seulement lorsque le standard ne porte pas la règle confirmée.

*** interface

react porte l'unique surface utilisateur publique sous =/app/=. django conserve la passerelle, les sessions techniques et les contrats http, sans écran métier parallèle.

*** authentification et comptes

la cible initiale est une session odoo relayée par django : le navigateur s'authentifie auprès de django en https, django vérifie les identifiants auprès d'odoo via la passerelle centrale, puis conserve uniquement une session technique révocable. aucun mot de passe odoo n'est stocké en clair dans django, une session ou les journaux.

la base existante de =csrs_report= sur =report.ent.koba.sarl= est la source autorisée pour créer les comptes odoo et reprendre l'organigramme. elle est consultée en lecture seule; la migration est une commande explicite avec simulation, rapport d'écarts, clés stables et reprise sans doublon. après validation, odoo devient la seule source de vérité.

les alternatives non retenues pour le premier lot sont :

- oauth/oidc : délègue l'identité à un fournisseur standard et évite de transmettre le mot de passe à CSRS ENT, mais exige un fournisseur configuré et une intégration odoo correspondante.
- sso institutionnel : expérience de connexion unique à l'échelle de l'établissement, généralement bâtie sur oidc ou saml, mais dépend de l'infrastructure d'identité institutionnelle.

*** branches

le dépôt utilise exactement trois branches : =dev= pour l'intégration, =preprod= pour le commit déployé sur cet hôte et =prod= pour la production. une promotion réutilise le même commit validé de =dev= vers =preprod= puis =prod=. les noms =main= et =master= ne seront pas maintenus comme alias sans décision explicite.

** approche de réalisation

le code suit un cœur fonctionnel fortement typé et une enveloppe impérative limitée à django, rpc et odoo. les règles de validation, normalisation et correspondance sont déterministes et testables sans réseau; les entrées non fiables sont converties dès la frontière vers des types précis et, lorsque possible, immuables.

chaque comportement commence par un test lisible given/when/then. les fonctions pures ont des tests unitaires, la passerelle a des tests de contrat, django a des tests http et odoo a des tests transactionnels des règles métier, acl, règles d'enregistrement et conflits de révision. les parcours critiques react recevront des tests de composant et des tests comportementaux navigateur.
