* Décisions confirmées

** architecture

odoo est le système d'enregistrement unique. django ne possède aucun modèle métier : il sert de façade web/api, porte les sessions techniques et appelle odoo par une passerelle centralisée. un stockage technique futur de sessions, files ou caches ne devra contenir aucun objet métier odoo.

le module odoo =csrs_reporting= réutilise =res.users=, =res.partner=, =hr.department=, =hr.employee=, =project.project= et =project.task=. le premier lot étend =project.task= avec un responsable csrs, une révision optimiste et une progression; chaque évolution crée une entrée append-only =csrs.progress.entry= dans la même base odoo.

le portage n'est pas une réplication automatique des tables de =csrs_report=. chaque capacité est rapprochée d'un modèle odoo standard, puis complétée dans odoo seulement lorsque le standard ne porte pas la règle confirmée.

** interface

l'interface combine django et react avec un accent sur react, dans la continuité de l'application actuelle. react porte progressivement les parcours principaux; django conserve la passerelle, les sessions, les réponses serveur utiles et les écrans non encore migrés. le routage précis sera fixé avant le premier lot frontend.

** authentification et comptes

la cible initiale est une session odoo relayée par django : le navigateur s'authentifie auprès de django en https, django vérifie les identifiants auprès d'odoo via la passerelle centrale, puis conserve uniquement une session technique révocable. aucun mot de passe odoo n'est stocké en clair dans django, une session ou les journaux.

la base existante de =csrs_report= sur =report.ent.koba.sarl= est la source autorisée pour créer les comptes odoo et reprendre l'organigramme. elle est consultée en lecture seule; la migration est une commande explicite avec simulation, rapport d'écarts, clés stables et reprise sans doublon. après validation, odoo devient la seule source de vérité.

les alternatives non retenues pour le premier lot sont :

- oauth/oidc : délègue l'identité à un fournisseur standard et évite de transmettre le mot de passe à pent, mais exige un fournisseur configuré et une intégration odoo correspondante.
- sso institutionnel : expérience de connexion unique à l'échelle de l'établissement, généralement bâtie sur oidc ou saml, mais dépend de l'infrastructure d'identité institutionnelle.

** branches

le dépôt utilise exactement trois branches : =dev= pour l'intégration, =preprod= pour le commit déployé sur cet hôte et =master= pour la production. une promotion réutilise le même commit validé de =dev= vers =preprod= puis =master=. le nom =main= ne sera pas maintenu comme quatrième alias sans décision explicite.

* source de migration vérifiée

inventaire agrégé en lecture seule du 2026-08-14 :

- 42 comptes, tous actifs, avec email et alias; un seul compte administrateur global.
- 42 empreintes de mot de passe django =pbkdf2_sha256=; aucune empreinte ni donnée personnelle n'a été affichée ou journalisée.
- 50 unités, dont 43 actives, et 47 liens entre unités.
- 47 appartenances, dont 41 appartenances principales ouvertes.
- 40 lignes hiérarchiques principales ouvertes et aucune ligne secondaire ouverte.

correspondance initiale proposée :

| source =csrs_report=     | cible odoo                                                | règle                                                                        |
|--------------------------+-----------------------------------------------------------+------------------------------------------------------------------------------|
| =accounts_user=          | =res.users= + =res.partner= + =hr.employee=               | email comme login proposé; conserver alias, nom, fonction, téléphone et état |
| =organizationunit=       | =hr.department=                                           | conserver code stable, libellés et état actif                                |
| =organizationunitlink=   | hiérarchie =hr.department=                                | rejouer après création de toutes les unités; refuser les cycles              |
| =organizationmembership= | rattachement employé + extension csrs datée si nécessaire | préserver unité principale et périodes sans écraser l'historique             |
| =reportingline=          | responsable de l'employé + extension csrs datée           | préserver principal/secondaire et périodes; appliquer les règles odoo        |

les 42 empreintes django =pbkdf2_sha256= sont transférées par un fichier temporaire protégé, sans affichage ni journalisation. odoo les accepte transitoirement et les convertit vers son propre schéma après la première connexion réussie; une réimportation ne rétrograde jamais une empreinte déjà convertie.

* besoins fonctionnels repris de csrs

- une saisie courte et responsive, utilisable sur téléphone et ordinateur.
- un responsable principal peut créer, modifier, valider et fermer; un responsable secondaire peut voir et commenter.
- le reporting est hebdomadaire et une progression à 100 % exige une validation du responsable principal.
- les affectations, validations et changements de progression restent auditables.
- les autorisations sont appliquées côté serveur et les écritures concurrentes utilisent une révision explicite.

* approche de réalisation

le code suit un cœur fonctionnel fortement typé et une enveloppe impérative limitée à django, rpc et odoo. les règles de validation, normalisation et correspondance sont déterministes et testables sans réseau; les entrées non fiables sont converties dès la frontière vers des types précis et, lorsque possible, immuables.

chaque comportement commence par un test lisible given/when/then. les fonctions pures ont des tests unitaires, la passerelle a des tests de contrat, django a des tests http et odoo a des tests transactionnels des règles métier, acl, règles d'enregistrement et conflits de révision. les parcours critiques react recevront des tests de composant et des tests comportementaux navigateur.
